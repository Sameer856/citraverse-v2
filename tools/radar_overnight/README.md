# Overnight radar comparison

Run `caffeinate -i /private/tmp/citra-cloud-venv/bin/python -u tools/radar_overnight/run.py` from the project root. Requires the existing ignored `.cloud-local/pairing.json`, `httpx`, and `websockets`. Never copy credentials into the source or the report.

The 2026-11-25/26 experiment compares temporary profiles through the existing authenticated GCP RPC, records compressed RDR2 and per-frame metrics locally, verifies command replies and fresh frames, repeats a shortlist, and restores the original active profile. It never saves experimental settings to NVS or flashes firmware. It does not run noise calibration while the bed is occupied. Planned finish: 07:00 IST, 2026-11-26. Sequential screening uses 8-minute windows; shortlisted settings use repeated 20-minute windows. Clock times and actual durations are logged.

Mount geometry is transcribed from the supplied screenshots: 3 × 3 × 3 m room, far-left corner 15 cm from walls, radar height 2 m, roll 180°, down tilt 10°, heading toward centre (135°). Exact bed dimensions are not confirmed. Initial analysis uses the existing dashboard default: width 1 m, length 2 m, height 0.55 m, wall gap 0.15 m, at far-right pointing near-right. Bed ROI includes a margin; report sensitivity to this assumption.

Bed return persistence, both bed-half occupancy and outside-zone clutter are proxy measures. They do not establish person count, detection accuracy, sleep state, breathing, or fall performance. A bed or blanket can itself create persistent static returns. Two people remaining in bed is user-supplied context, not synchronized ground truth. Do not call the highest proxy score an objectively optimal detector. Empty-bed and one-person controls are still needed.

Outputs are private local experiment evidence in `output/radar_overnight_20261125/`. `.rdr.gz` consists of little-endian float64 receive epoch + uint32 payload bytes + RDR2 payload, repeated. Metrics JSONL and event/readback logs allow independent replay. Do not commit raw occupancy recordings or pairing credentials to GitHub.

Four observed PCB restarts interrupted experimental comparisons. Their cause is unknown; interrupted/mixed-profile windows are excluded from stable rankings and retained as fault evidence. Further hardware sweeps are suspended. `RADAR_OBSERVE_ONLY=1` verifies the original working active profile and records successive 20-minute windows without reapplying an already healthy profile. The currently running baseline uses literal `mmwc cfar 1 80`, 58 GHz, range 6400/25, velocity 3200/200, 50 ms frames and clutter removal off. No occupied-room noise estimate is performed.

Capture instrumentation revision 2 runs periodic status/RPC requests asynchronously so they do not pause WebSocket consumption. Earlier windows can contain collector-induced receive gaps during synchronous status checks. A missing health reply is not counted as a reboot; boot ID, known frame-counter decreases and stream index resets are audited independently.

Offline spatial and temporal grids use development windows only to choose a frozen bed-aligned grouping method. `frozen-bed-method-v2.json` records selection time and parameters. Only complete baseline windows starting after that time qualify as prospective validation. `replay_runtime.mjs` replays the actual dashboard classes, checks their source hash, and reports fresh bed candidates separately from weak retained evidence. Candidate counts are not labeled human counts. `watch_analysis.py` updates analyses for newly completed windows without changing hardware. Run it with the same cloud Python environment; its temporal subprocess uses the installed bundled NumPy runtime.

## Bounded static-return repeat

The aggressive frequency/explicit-CFAR sweep remains stopped. After a prolonged stable baseline, `crossover.py` can repeat only the previously successful literal-CFAR static-retention flag (`static_rm=0`) for two consecutive 20-minute windows, restore the original baseline for 20 minutes, then continue baseline-only observation. This changes no other requested parameter, Wi-Fi, firmware or startup save. It aborts additional alternate windows on a reboot, stale-radar status, failed fresh-rate gate or external operator change. Set `RADAR_CROSSOVER_EXPECTED_BOOT` to the just-verified boot ID to refuse a test after a new reset. The execution plan and any recovery are logged separately; the earlier suspension record is retained. Rollback and external-change handling have simulated control-flow tests.

`density_bed.py` is a separate exploratory density-core grid, trained only on windows 000, 003, 008 and 009. Its frozen candidate is replayed by `replay_density_runtime.mjs` with the exact JavaScript tracker. It does not overwrite the earlier method or its independent results. Each frozen engine has a source hash; changes must not silently redefine its prospective validation. Pre-freeze comparisons, selected development windows, prospective baseline windows and prospective alternate profiles are labeled separately. Retained historical-only candidates do not count as recent detections.

Capture revision 3 checks status even while the WebSocket reports waiting. Thirty seconds without newly indexed fresh frames aborts a comparison; valid fresh frames with no point returns keep the stream alive. Interrupted packet files receive unique names. `evaluate_crossover.py` applies the criteria recorded before the alternate windows and never changes hardware. Unknown counters or missing exact replay do not count as proof of improvement.

## Final candidate and holdout

`select_method.py` is read-only. It waits for the complete crossover decision, uses only completed post-freeze windows on the chosen hardware before the recorded selection cutoff, and compares the two frozen methods. Density must justify its longer geometry history with a practical two-group gain; otherwise the earlier 200 ms method remains preferred. The bounded display policy has a separate prospective comparison and never relaxes fall-state continuity.

After reviewing that result, freeze `final-method-selection.json` with the selected profile, method/options, strict or bounded display policy, engine hashes, expected boot ID, selection reference, planned capture end, and a snapshot of the holdout criteria. `observe_selected.py` validates that one candidate through the remaining night. It never saves startup settings. A stall, reboot or failed fresh-rate/age check requests the original baseline permanently; a process restart preserves that fallback. External operator profiles are not overwritten. `evaluate_final.py` audits only matching post-selection windows, reports missing telemetry as unverified, and separates regressions from successful windows. The final holdout is not used to refit parameters.

All two-group numbers are unverified spatial proxies. Bed dimensions remain an explicit assumption. The calculated physical aiming guide is not a measured antenna pattern, and software coordinates must not be changed to imitate a physical remount.

An aborted crossover is a terminal failed selection gate even when its post-baseline window is missing. Closed software-selection periods with too little eligible completed data are inconclusive, rather than pending forever or declared successful. A conservative retained default must be recorded explicitly, with its reference window and rationale, before a new independent observation begins.

`return_maps.py` adds descriptive room-cell plots for the baseline reference, observed alternate windows and matching final observation. It samples one fresh frame per receive-second, counts each 10 cm cell at most once in that frame, and uses the same world transform and height slice for every panel. The maps do not identify people or fit parameters. `report.py` refreshes this cached descriptive analysis when generating the PDF and the inline-data Canvas source. Report generation does not contact the PCB or GCP. The final report must disclose interrupted comparisons, unconfirmed bed dimensions and any regressions, even when a partial alternate result looks better.

`watch_health.py` retains the collector's existing local `progress.json` snapshots in `late-health-snapshots.jsonl`; it makes no additional network or device requests. It preserves reported heap and selected transport/storage counters after its actual start time. Missing reset reasons, internal-heap breakdown and earlier telemetry cannot be reconstructed from these late snapshots. Counter changes across a restart must not be treated as ordinary within-boot differences.

`transport_audit.py` independently scans packet headers and verifies its frame totals and receive gaps against completed-window collector summaries. If a reconnect-timing hypothesis was recorded before follow-up observations, it compares the original predicted times without refitting them. An intervening recorded outage makes the old connection schedule interrupted; it is not treated as successful timing validation. The [Cloud Run WebSocket reference](https://docs.cloud.google.com/run/docs/triggering/websockets) and the local 3,600-second deployment setting support a possible timeout explanation, not a verified live-service cause. No transport setting is changed by this analysis.
